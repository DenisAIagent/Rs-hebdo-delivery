| Question | Verdict | Gravité |
|---|---|---|
| **1. Peut-on voler ma base clients (journalistes) ?** | 🟢 **Non aujourd'hui** — mais protection *accidentelle*, à une migration de la catastrophe | latent CRITIQUE |

| **3. Peut-on gruger sur les paiements ?** | 🟢 **Sans objet** — aucun Stripe/paywall/abonnement. MAIS vol de *valeur* : quota IA + écriture WordPress abusables par un compte journaliste | 🟠 ÉLEVÉE |

### LA faille urgente

> **La RLS de toute la base est cassée par une récursion infinie (`42P17`) et ne « tient » qu'en échouant. La clé anon est publique (dans le bundle JS). Le jour où quelqu'un « répare » cette erreur de la façon la plus courante (`ALTER TABLE profiles DISABLE ROW LEVEL SECURITY`, ou en restaurant naïvement les policies admin), la base journalistes (emails, noms, rôles), tous les papiers, ET les secrets de production en clair (`app_settings`) deviennent lisibles d'un simple `curl` anonyme.**
>
> Correctif à appliquer **avant ou en même temps** que la correction de la récursion, jamais après : `REVOKE ALL ON app_settings FROM anon, authenticated;` + refonte des policies via une fonction `is_admin()` en `SECURITY DEFINER`.

## Q1 & Q2 — Vol de base & isolation inter-journalistes

### Confirmé en live

Requête anonyme (clé publishable extraite du bundle) sur **chaque** table sensible :

```
GET /rest/v1/profiles         → HTTP 500  {"code":"42P17","message":"infinite recursion detected in policy for relation \"profiles\""}
GET /rest/v1/deliveries       → HTTP 500  42P17
GET /rest/v1/delivery_logs    → HTTP 500  42P17
GET /rest/v1/paper_types      → HTTP 500  42P17
GET /rest/v1/hebdo_config     → HTTP 500  42P17
GET /rest/v1/app_settings     → HTTP 500  42P17
GET /rest/v1/correction_prompt→ HTTP 500  42P17
```

**Zéro ligne rendue à un anonyme.** Aucune fuite active. Testé aussi : `GET /auth/v1/settings` → `disable_signup:false`, `mailer_autoconfirm:false` (inscription ouverte mais e-mail à confirmer, et **pas de trigger créant un profil** → un auto-inscrit obtient un compte `auth.users` sans ligne `profiles` → `authMiddleware` renvoie **403 « Compte desactivé »**. L'inscription libre ne donne donc aucun accès applicatif).

### Cause racine — CRITICAL (latent)

`supabase-schema.sql:77-87` (idem `supabase/migrations/20260325000000_initial_schema.sql:69-79`) :

```sql
CREATE POLICY "Admins can read all profiles" ON profiles FOR SELECT
  USING ( EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'admin') );
CREATE POLICY "Admins can manage profiles" ON profiles FOR ALL
  USING ( EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'admin') );
```

Une policy **sur `profiles`** qui lit **`profiles`**. À la réécriture (`fireRIRrules`), Postgres ré-applique la RLS de `profiles` dans le sous-select → détection de récursion → **`ERROR 42P17`, avant toute planification**. Les policies permissives étant OR-ées, `"Users can read own profile" USING (auth.uid() = id)` ne sauve rien : l'erreur est levée avant tout court-circuit booléen. Et comme **toutes** les autres tables ont une policy admin `EXISTS (SELECT 1 FROM profiles …)`, la contamination est totale (`deliveries` `:126-130`, `paper_types` `:94-104`, `app_settings` `:241-251`, `delivery_logs` `:149-153`, `correction_prompt` via `20260825120000_rls_logs_prompt.sql:25-31`).

Le backend n'est pas impacté car `backend/src/utils/supabase.ts:10` utilise `SUPABASE_SERVICE_KEY` (`BYPASSRLS`). **C'est pourquoi l'app marche alors que la RLS est morte — et pourquoi personne ne l'avait vu.**

|---|---|---|---|---|

| `paper_types` | 42P17 | 42P17 | 42P17 | fail-closed |

| `delivery_logs` | 42P17 | 42P17 | 42P17 | fail-closed |

| `auth.users` | inaccessible | inaccessible | inaccessible | non exposé par PostgREST |

### Ce qui est bien protégé (à ne pas casser)

- **Le frontend ne lit aucune table directement** : `grep` sur `frontend/src` ne remonte que `supabase.auth.*` (login, session, MFA, reset password). Tout le data-flow passe par l'API Express. La RLS cassée est donc invisible en prod.
- **`authMiddleware` (`backend/src/middleware/auth.ts`)** valide le token via `supabaseAdmin.auth.getUser(token)` (non spoofable) et lit le rôle **en base**, jamais depuis le JWT client ni un header.
- **`adminMiddleware`** vérifie `req.userRole === 'admin'` côté serveur. Testé live sans token : `/api/admin/*`, `/api/deliveries`, `/api/correct` → **401**. `/api/admin/journalists`, `/api/admin/settings` → 401.
- **Pas d'IDOR** : `GET /api/deliveries`, `GET /:id`, `PUT /:id` filtrent tous par `.eq('author_id', req.userId)` (`deliveries.ts:82, 465, 505`). L'attribution d'un papier à un autre auteur est réservée aux admins (`deliveries.ts` bloc `rawAuthorId` → 403 si non-admin).

### Correctif Q1/Q2

Ordre impératif : **1 avant 2.**

1. Verrouiller les tables sensibles au seul `service_role` (le backend n'a besoin de rien d'autre) :
   ```sql
   REVOKE ALL ON app_settings, profiles, deliveries, delivery_logs, correction_prompt
     FROM anon, authenticated;
   ```
2. Casser la récursion avec une fonction `SECURITY DEFINER` (elle ne re-déclenche pas la RLS) :
   ```sql
   CREATE OR REPLACE FUNCTION public.is_admin() RETURNS boolean
     LANGUAGE sql SECURITY DEFINER SET search_path = public AS
     $$ SELECT EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'admin') $$;
   -- puis remplacer chaque EXISTS(...) par public.is_admin() dans toutes les policies
   ```
3. **Ne jamais** « corriger » par `DISABLE ROW LEVEL SECURITY` : cela ouvrirait `profiles`/`deliveries` en lecture publique via la clé anon du bundle.
4. **En réécrivant les policies, corriger deux pièges qui s'activeront dès la fin de la récursion** :
   - `hebdo_config` a `USING (true)` (`supabase-schema.sql:107-109`) → calendrier éditorial (numéros, dates de bouclage) lisible par **anon** dès le fix. Remplacer par `USING (auth.uid() IS NOT NULL)`.
   - **Aucune** policy ne porte de clause `TO` → toutes visent `PUBLIC` (donc `anon`). Ex. `paper_types USING (is_active = true)` deviendrait lisible **sans authentification**. Ajouter `TO authenticated` sur les 16 policies.

## Q3 — « Paiement » → vol de valeur

**Confirmé : aucun Stripe, aucun paywall, aucun abonnement.** Grep exhaustif (`stripe|paddle|subscription|has_paid|billing|checkout|trial`) → 2 faux positifs (listener Supabase `onAuthStateChange`, commentaire). `profiles.role ∈ {journalist, admin}` uniquement. **Aucun vecteur de contournement de paiement.**

La valeur volable est ailleurs, et **exploitable dès aujourd'hui par un compte journaliste provisionné** :

### 🟠 HIGH — `POST /api/deliveries` déclenche le pipeline WordPress sans rate limit dédié

`backend/src/routes/deliveries.ts:450` lance automatiquement, sans contrôle de rôle ni limiteur propre :

```ts
void publishDeliveryToWordpress({ deliveryId, title, ..., bodyText, images })
```

Chaque appel effectue : un appel **Claude à `max_tokens: 16384`** (`wordpressPublisher.ts:222`), jusqu'à **15 créations de tags** dans la taxonomie de prod (`wordpress.ts:198`), **N uploads** dans la médiathèque de `rollingstone.fr` (`wordpress.ts:237`), et la création d'un **brouillon**. Seul garde-fou : le limiteur **global** `300 req / 15 min / IP` (`index.ts:67-73`) — soit ~1200 appels Claude/heure possibles. `/api/correct`, lui, est correctement limité (30/h/user, `correction.ts:9-16`) ; `/api/deliveries` ne l'est pas.

**Impact :** un journaliste (ou un compte journaliste compromis) peut brûler le quota Anthropic du propriétaire et polluer en boucle la médiathèque + la taxonomie de rollingstone.fr.
**Correctif :** ajouter un `rateLimit` dédié par `userId` sur `POST /api/deliveries` (ex. 20/h), et découpler la publication WP dans une file (BullMQ) avec quota.

### Ce qui est bien protégé

- **WordPress = toujours un brouillon** « [EN ATTENTE DE RELECTURE] » (`wordpressPublisher.ts:378` → `createWpDraftPost`, statut `draft`). **Un journaliste ne peut jamais publier en ligne** sur rollingstone.fr. La republication est réservée aux admins (`admin.ts:746`, `adminMiddleware`).
- **MFA appliqué côté serveur** : `authMiddleware:40-42` rejette tout JWT non-`aal2` quand `REQUIRE_MFA` est actif — le contournement du state React ne sert à rien, le backend re-vérifie à chaque requête. *(Actuellement `mfaRequired:false` en prod — confirmé live via `/api/auth/config`.)*
- **Escalade de privilège** : aucun endpoint ne permet à un journaliste d'écrire son propre `role`. La modification de rôle est admin-only (`admin.ts:319`) avec protection anti-suppression du dernier admin.

## Q4 — Secrets & accès

### Confirmé en live / statique — rien de vif exposé

- **Aucun secret réel** dans le dépôt : scan `sk-ant-`, `sk_live_`, `whsec_`, `re_`, `AIza`, JWT `eyJ…`, clés privées, mots de passe applicatifs → **RAS**. Seuls `*.env.example` avec placeholders. **Pas de `.git`** (rien de versionné). `macos/` (secrets bakés mentionnés au `.gitignore`) **supprimé localement**.
- **Bundle navigateur propre** (`frontend/dist/assets/index-rs-0soa9.js`) : **aucune sourcemap**, aucune clé, aucune URL Supabase. Seules 3 variables `VITE_` référencées (URL Supabase, clé **publishable**, URL d'API) — **attendues et sûres**.
- **En-têtes de sécurité** (testés live sur `/`) : CSP complète, `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex`. Solide.
- **CORS** : `Origin: https://evil.com` sur `/api/health` → **non réfléchi** (whitelist `FRONTEND_URL` en prod, `index.ts:47-63`). Bon.
- **`/api/admin/settings` masque les secrets** (`admin.ts:798-804`) : `••••••••` + 4 derniers caractères. Aucun secret renvoyé en clair au navigateur.
- **Upload** : `multer` en mémoire, 60 Mo/fichier, 30 fichiers max, SVG refusé, **vérification des magic bytes** (`assertRealImages`, `deliveries.ts`), HTML strippé des métadonnées. Bien fait.

### 🟠 HIGH (ACTIF) — Le mot de passe d'application WordPress fuit en clair dans les logs Railway

Contrairement au reste de Q4, **rien ne bloque ce chemin aujourd'hui.** `wpClient()` (`backend/src/services/wordpress.ts:128`) porte un header `Authorization: 'Basic ' + base64(username:appPassword)`. Deux chemins d'erreur rethrowent l'`AxiosError` brute (`wordpress.ts:206`, `:305`), et deux appelants la passent telle quelle à `console.error` :

```ts
// deliveries.ts:459
}).catch((err) => console.error('[WordPress] Unexpected publish error:', err));
// admin.ts:756
console.error('Admin send to WordPress error:', error);
```

`console.error` sur un objet utilise `util.inspect` (profondeur 2). `err.config.headers` est à la profondeur 2 : ses valeurs string sont imprimées **intégralement**, `Authorization: 'Basic cnNfZGVsaXZlcnk6…'` compris → décodage base64 immédiat du couple utilisateur / mot de passe applicatif de `rollingstone.fr`, lisible par tout porteur d'accès au projet Railway. À l'inverse, `services/dropbox.ts:53,178` logge proprement `err?.response?.data || err.message` — c'est le modèle à généraliser.

**Correctif :** aux deux lignes, `console.error('[WordPress] …:', err?.response?.data || err?.message || String(err))`. En défense en profondeur, intercepteur sur `wpClient` qui `delete error.config.headers.Authorization` avant rethrow. Même vigilance sur les ~35 `console.error('…', error)` de `routes/admin.ts`.

### 🟠 HIGH (latent) — Secrets de prod en clair dans `app_settings`

`supabase-schema.sql:231-263` : `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `MISTRAL_API_KEY`, `DROPBOX_APP_KEY`, `DROPBOX_APP_SECRET`, `DROPBOX_REFRESH_TOKEN`, `WORDPRESS_APP_PASSWORD` stockés en `TEXT` **non chiffré**. Le masquage backend est purement cosmétique (couche présentation).

**Réconciliation live :** la chaîne d'attaque « JWT admin `aal1` → `GET /rest/v1/app_settings` via la clé anon → dump des secrets » **échoue aujourd'hui** (la lecture renvoie `42P17`, cf. Q1). Ce n'est pas un contrôle voulu, c'est la policy cassée. **Risque latent** : dès que la récursion est « réparée » en restaurant les policies admin, ces secrets deviennent lisibles avec un simple mot de passe admin (le TOTP ne protège pas PostgREST — aucune policy ne teste l'AAL). D'où l'ordre du correctif : **REVOKE d'abord**.

**Impact des secrets exposés :** `DROPBOX_REFRESH_TOKEN` (non périmable) = accès permanent à tous les papiers/photos de tous les journalistes ; `WORDPRESS_APP_PASSWORD` = écriture sur rollingstone.fr.

**Correctif :**
1. `REVOKE ALL ON app_settings FROM anon, authenticated;` (cf. Q1).
2. Migrer les 6 valeurs sensibles vers les variables d'environnement Railway (le backend lit déjà `process.env` en priorité — `setup.ts:16-20`, `claude.ts`, `wordpress.ts` — bascule transparente). À défaut : Supabase Vault / `pgsodium`.
3. **Rotation de toutes ces clés** : elles sont en clair depuis la mise en service.

### 🟡 MEDIUM

- **Wizard de setup rouvrable après perte de base (latent, scénario déjà survenu)** : `/api/setup/configure` (`setup.ts`) est public (monté avant tout middleware, `index.ts:81`). `isAppConfigured()` exige spécifiquement `ANTHROPIC_API_KEY` (`setup.ts:6-11`) même si `AI_PROVIDER` vaut `gemini`/`mistral` → peut renvoyer `false` en permanence. Surtout, **la base a déjà été perdue une fois** (pause Supabase 90 j). Si `app_settings` est vide **et** que `SETUP_SECRET_TOKEN` est reposé sur Railway, la boucle d'upsert **sans allow-list** (`setup.ts:92-119`) accepte n'importe quelle clé : `DROPBOX_*` (détournement des papiers), `WORDPRESS_URL`/`WORDPRESS_APP_PASSWORD` (détournement des publications), **`REQUIRE_MFA=false` (2FA coupée pour toute la rédaction)**. Elle ne peut PAS créer d'admin (écrit seulement `app_settings`). *Bloqué aujourd'hui : le token n'est pas défini sur Railway (403 live) et le front n'envoie jamais `x-setup-token`.* → Correctif : `if (process.env.SETUP_ENABLED !== 'true') return res.status(404)`, **allow-list stricte** (jamais `REQUIRE_MFA`), limiteur 5/h/IP, `crypto.timingSafeEqual`, et retirer `SETUP_SECRET_TOKEN` de Railway.
- **Injection de prompt → HTML non assaini dans un brouillon de prod** : le texte du journaliste passe à Claude, dont le `contentHtml` est inséré **verbatim** dans le brouillon WP (`wordpressPublisher.ts:290,380`). `stripHtml` amont nettoie le HTML brut des métadonnées mais pas une instruction en langage naturel poussant l'IA à générer le HTML voulu. Atténué par `status:draft` + relecture humaine. → `sanitize-html` (allowlist stricte) avant `createWpDraftPost` + compte applicatif WP en rôle `Contributor`, pas `Editor`.
- **`sign_limit` jamais vérifié côté serveur** + `multer` sans `fieldSize` : un corps de ~1 Mo part chez Anthropic à `max_tokens:16384` sans plafond métier (grep : `sign_limit` n'apparaît que dans des `select`). → `fieldSize: 200*1024` + rejet si `bodyText.length > sign_limit * 1.5` avant l'appel IA.
- **`maskValue` divulgue les 4 derniers caractères** (`admin.ts:798-804`) : pour un mot de passe applicatif WP (`xxxx xxxx…`, 24 car.), c'est **1/6 du secret** livré à l'UI admin (donc à tout XSS/capture d'écran). → renvoyer `isSet: boolean` + `updated_at`, sans suffixe.
- **CSP `script-src 'unsafe-inline'`** (`index.ts:32`) : affaiblit la protection XSS. Nonces par requête ou retrait de l'inline. Crisp chargé inline sans SRI.
- **`isMfaRequired()` fail-open** : en cas d'erreur de lecture de `app_settings`, la politique MFA retombe silencieusement à `false` (`mfaPolicy.ts`, `auth.ts` catch). Un incident base = MFA désactivé sans alerte. Fail-**closed** attendu.
- **Contenu éditorial non publié + PII dans `HEBDO4septembre/`** : `.docx`, images, noms de journalistes dans l'arbre de travail. À exclure de tout partage/build.

### 🟢 LOW

- **`/api/setup/status`** (public) et **`/api/auth/config`** (public) divulguent l'état de configuration et la politique MFA. Divulgation mineure.
- **`POST /api/deliveries/ensure-hebdo`** : un journaliste peut créer des numéros d'hebdo (1-9999), rate-limité 5/h. Pollution mineure.
- **`PUT /api/deliveries/:id`** : l'`UPDATE` final ne filtre que par `id`, mais la propriété a déjà été vérifiée juste avant (fetch `id`+`author_id`). Sans impact (TOCTOU théorique). Ajouter `.eq('author_id', req.userId)` à l'`UPDATE` par défense en profondeur.
- **Divergence schéma / migrations** : `supabase-schema.sql` (colonnes `fields_config`, `start_date/end_date`) et `supabase/migrations/*` décrivent des états différents ; ni l'un ni l'autre ne reflète la prod (d'où la nécessité du test live). Faire des migrations la source de vérité unique (`supabase db diff` de rattrapage), réduire `supabase-schema.sql` à un pointeur.
- **Policies `FOR ALL` sans `WITH CHECK`** : sans effet tant que l'accès est révoqué à `anon`/`authenticated`.

### ✅ Vérifié sain (faux positifs écartés)

- **Gating `/admin`** : l'UI est cachée côté React **et** les données sont protégées côté serveur (`authMiddleware` + `adminMiddleware`, rôle lu en base). Forcer la route `/admin` dans le navigateur ne donne accès à rien — testé live (401/403). Pas de faille.
